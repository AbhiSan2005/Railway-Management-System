Database Architecture: ER Diagram Simplification & Normalization

Comprehensive guide explaining the translation of the ER diagram, normal forms, and MySQL integrity constraints.

1. Why and How the ER Diagram was Simplified

The original ER diagram is comprehensive but contains non-core peripheral models. Here is how we streamlined it into a clean, high-performance relational schema:

Original ER Element ER Feature Type Design Decision & Simplification
PASSENGER.address Composite Attribute (street, city, state, pincode) Decomposed into 4 atomic fields in passengers table (1NF compliance).
PASSENGER.age Derived Attribute (dashed oval) Eliminated redundancy. Calculated from dob dynamically using MySQL GENERATED ALWAYS AS VIRTUAL.
PASSENGER.phone_numbers Multivalued Attribute (double oval) Primary phone stored in passengers; secondary phones mapped to passenger_phones table.
NEXT_OF_KIN Weak Entity (identifying relationship with PASSENGER) Retained in SQL schema with composite PK (passenger_id, kin_name) and ON DELETE CASCADE.
SCHEDULE Weak / Associative Entity between TRAIN and STATION Mapped with PK (train_id, stop_sequence) and FK to stations(station_id).
SEAT & COACH Weak Entity SEAT dependent on COACH Hierarchical relationship: trains → coaches → seats. For fast queries, tickets record coach_id and seat_number.
EMPLOYEE HR Entity (WORKS_ON train, STATIONED_AT station) Decoupled from booking transaction flow to keep booking queries lean and fast.

2. Step-by-Step Normalization Analysis

1NF

First Normal Form

  • Rule: Each column must contain atomic (indivisible) values, and no repeating groups.
  • In our ER:
    • Decomposed composite address into street, city, state, pincode.
    • Decomposed multivalued phone_numbers into child table passenger_phones.
    • Removed derived age attribute to prevent stale/inconsistent data.
2NF

Second Normal Form

  • Rule: Must be in 1NF and have No Partial Functional Dependency (no non-prime attribute can depend on a proper subset of a composite candidate key).
  • In our ER:
    • schedules has composite key (train_id, stop_sequence). Attributes like arrival_time and departure_time depend on the entire pair.
    • Station metadata (e.g., station_name, zone) is strictly isolated in stations table, preventing partial dependency.
3NF

Third Normal Form

  • Rule: Must be in 2NF and have No Transitive Functional Dependency ($X \to Y \to Z$ where $Z$ is non-prime).
  • In our ER:
    • In tickets table, we store only passenger_id, train_id, and coach_id. We do NOT store passenger name, train name, or coach type.
    • Storing passenger name in tickets would create: ticket_id → passenger_id → passenger_name (transitive dependency).
BCNF

Boyce-Codd Normal Form

  • Rule: For every functional dependency $X \to Y$, $X$ must be a superkey.
  • All tables in this simplified schema strictly adhere to BCNF because all determinants are candidate keys or primary keys.

3. Integrity Constraints Implemented in MySQL

PRIMARY KEY (PK)

Enforces entity integrity (uniqueness and non-nullability). E.g., station_id, train_id, and composite keys like (coach_id, seat_number).

FOREIGN KEY (FK) & Referentials

Enforces referential integrity. Configured with ON DELETE CASCADE for child tables (like coaches and schedules) and ON DELETE RESTRICT for tickets to prevent accidental deletion.

UNIQUE Constraint

Prevents duplication. E.g., UNIQUE (train_id, coach_id, seat_number, journey_date) prevents the critical bug of double-booking the same seat.

CHECK Constraints

Enforces domain validity. E.g., CHECK (distance_km > 0), CHECK (fare > 0), and CHECK (source_station_id != destination_station_id).

NOT NULL & DEFAULT

Mandatory fields are flagged NOT NULL. Sensible defaults applied like booking_date DEFAULT CURRENT_TIMESTAMP and status DEFAULT 'CONFIRMED'.

VIRTUAL GENERATED COLUMN

Computes age on-the-fly: TIMESTAMPDIFF(YEAR, dob, CURDATE()), ensuring age is always 100% accurate without maintenance.
